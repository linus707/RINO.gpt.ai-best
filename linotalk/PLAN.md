# 리노톡(LinoTalk) 계획서 — Phase 0

> 상태: 서버(Phase 2)와 한글 조합 엔진(Phase 4의 로직 부분)을 먼저 구현했습니다. 앱·키보드는 Mac 없이 진행하는 방법 결정 후 시작합니다.
> 서버 API의 최신 내용은 `server/README.md`가 기준입니다 (구현하면서 `refused` 오류 코드, `reply_reading`, 레벨 이름 `starter`/`beginner`/`intermediate`가 추가됨).
> 작성일: 2026-11-13

## 0. 먼저 알려드릴 것 3가지 (시작 전 확인 결과)

### ① 이 저장소에는 이미 다른 서비스가 살아 있습니다
이 폴더(`RINO.gpt.ai-best`)는 `linuscompany.co.kr`로 배포되는 웹앱(장부·POS·가격표)과 푸시 알림용 Cloudflare Worker(`worker/`)가 들어 있는 저장소입니다.

- 기존 파일은 **하나도 건드리지 않습니다.**
- 리노톡 관련 파일은 전부 **`linotalk/` 폴더 하나 안에만** 만듭니다. (요청하신 `server/`도 기존 `worker/`와 헷갈리지 않게 `linotalk/server/`에 둡니다.)
- 웹사이트 배포 스크립트는 정해진 파일만 복사하므로, `linotalk/` 폴더가 생겨도 사이트에는 영향이 없습니다.
- 이 저장소는 **공개(public)** 저장소입니다. 그래서 "비밀키를 깃에 넣지 않는다" 규칙이 특히 중요합니다.

### ② 저는 여기서 iOS 앱을 직접 빌드할 수 없습니다
제가 작업하는 환경은 리눅스 클라우드라서 Xcode와 iPhone 시뮬레이터가 없습니다. 그래서 검증을 이렇게 나눕니다.

| 대상 | 누가, 어떻게 확인하나 |
|---|---|
| 프록시 서버 | **제가** 여기서 직접 실행하고 테스트합니다 |
| 한글 조합 로직 등 순수 Swift 코드 | **제가** 테스트 실행을 시도합니다 (리눅스용 Swift 설치가 되는 경우. 안 되면 아래 자동 빌드로 대체) |
| 앱·키보드 빌드 | **GitHub의 맥 빌드 서버(자동 빌드)**로 매 Phase 확인 — 질문 9번에서 허락을 구합니다 |
| 실제 화면·타자 느낌 | **리노님이** Mac의 시뮬레이터에서 확인 (매 Phase마다 클릭 순서를 안내합니다) |

즉 "Phase가 끝날 때 항상 빌드 가능"은 자동 빌드로 증명하고, 화면 동작은 리노님이 봐주셔야 합니다. Mac이 없으면 이 프로젝트는 진행할 수 없습니다 (질문 1번).

### ③ 요구사항 중 미리 조정이 필요한 부분
솔직하게 먼저 말씀드립니다. 자세한 내용은 7장(위험요소)에 있습니다.

- **"1초 이내 후보 표시"**: 디바운스 0.35초 + AI 응답 시간을 합치면 처음 보는 단어는 1초를 넘을 수 있습니다. 캐시된 단어는 즉시 뜹니다. 실측 후 수치를 보고드리겠습니다.
- **"검수"의 한계**: 번역한 AI가 스스로 역번역해 확인하는 방식이라 100% 보증은 아닙니다. 배지는 "참고용 신호"입니다.
- **상세 패널(바텀 팝업)**: 키보드는 자기 영역 밖에 그림을 그릴 수 없습니다. 그래서 팝업이 화면 위로 올라오는 게 아니라 **자판 자리가 상세 패널로 바뀌는 방식**으로 만듭니다.
- **비밀번호 입력창**: iOS가 알아서 기본 키보드로 바꿔 버리므로 우리 키보드는 아예 뜨지 않습니다. 그래도 이메일·URL·인증번호 등에서는 코드로 한 번 더 막습니다.

│   ├── Package.swift
│   ├── Sources/
│   │   ├── HangulEngine/    (두벌식 오토마타 — 다른 것에 의존하지 않는 순수 Swift)
│   │   └── LinoCore/        (모델, 번역 클라이언트, 캐시, App Group 저장소, SM-2)

    ├── test/

## 4. 서버 API 명세

공통 규칙
- 헤더 `Authorization: Bearer <앱 토큰>` 필수. 없거나 틀리면 `401`.
- 요청 제한: 기기(익명 설치 ID)·IP 기준 분당 횟수 제한 → 초과 시 `429`.
- **서버는 입력 내용을 저장·기록하지 않습니다.** 로그에는 글자 수, 언어, 걸린 시간, 상태 코드만 남깁니다.
- 사용자 입력은 프롬프트에서 항상 "번역 대상 데이터"로만 감싸 넣습니다 (프롬프트 인젝션 방어).

### `POST /translate`
요청
```json
{ "text": "안녕하세요", "targets": ["en", "ja"], "level": "beginner" }
```
- `text`: 1~200자. 초과 시 `400`.
- `targets`: `en`, `ja` 중 1~2개. **한 번의 요청으로 두 언어를 같이 받습니다** (속도·비용 절약).

응답 `200`
```json
{
  "source": "안녕하세요",
  "results": [
    {
      "target_lang": "ja",
      "candidates": [
        {
          "text": "こんにちは",
          "reading": "konnichiwa",
          "reading_kana": "こんにちは",
          "sense": null,
          "back_translation": "안녕하세요(낮 인사)",
          "confidence": 0.95,
          "verdict": "ok",
          "note": "낮 시간대 인사. 아침엔 おはようございます",
          "register": "neutral",
          "flags": []
        }
      ]
    }
  ]
}
```
요청안 대비 추가한 필드 (가정)
- `sense`: 다의어 구분용 짧은 한국어 뜻. 예) "배" → `sense: "과일"` / `"탈것"` / `"신체"`
- `reading_kana`: 일본어 히라가나 읽기 (요청안의 `reading`은 로마자로 사용)
- `flags`: `["profanity"]`이면 상세 패널에 "비속어" 경고 표시
- 두 언어를 한 번에 받기 위해 최상위를 `results` 배열로 감쌌습니다.

서버 검증: AI 응답을 JSON 스키마로 검사 → 깨졌으면 **서버가 1회 재시도** → 그래도 실패면 `502 schema_error`. 앱도 받은 응답을 한 번 더 검사합니다.

### `POST /chat`
요청
```json
{
  "scenario": "cafe_order", "lang": "en", "level": "beginner",
  "history": [
    { "role": "assistant", "text": "Hi! What can I get for you?" },
    { "role": "user", "text": "I want coffee one." }
  ]
}
```
- 대화 기록은 **앱이 매번 보내고 서버는 기억하지 않습니다.** 최근 12턴, 턴당 300자 제한.

응답 `200`
```json
{
  "reply": "Sure! Hot or iced?",
  "reply_ko": "네! 따뜻한 걸로 드릴까요, 아이스로 드릴까요?",
  "correction": {
    "needed": true,
    "better": "I'd like a coffee, please.",
    "explanation_ko": "'coffee one'보다 'a coffee'가 자연스러워요."
  }
}
```

### `GET /health`
`{ "ok": true }` — 서버가 살아 있는지 확인용.

### 오류 형식 (공통)
```json
{ "error": { "code": "rate_limited", "message": "잠시 후 다시 시도해 주세요." } }
```
코드: `unauthorized`(401) · `invalid_input`(400) · `rate_limited`(429) · `schema_error`(502) · `upstream_error`(502) · `timeout`(504)

앱 쪽 오류 구분(3-C 요구사항): `offline` / `server` / `schema` / `rateLimited` / `cancelled`

## 5. 키보드 핵심 설계

### 5-1. 번역 요청 흐름
```
키 입력 → (한글이면) 오토마타가 조합 → 입력창에 반영
      → 마지막 어절 추출 → 번역해도 되는 입력창인지 확인
      → 캐시에 있으면 즉시 표시
      → 없으면 350ms 기다림(띄어쓰기를 누르면 즉시) → 이전 요청 취소 → 서버 요청(3초 제한)
      → 응답 검사 → 후보 줄에 표시 + 캐시에 저장
```
**어떤 경우에도 키 입력은 네트워크를 기다리지 않습니다.** 번역은 완전히 따로 돕니다.

### 5-2. 번역을 보내지 않는 경우
- 전체 접근이 꺼져 있을 때 (→ "전체 접근을 켜면 번역이 나와요" 안내)
- 입력창 종류가 이메일, URL, 숫자·전화번호, 아이디, 비밀번호, 인증번호, 카드 정보일 때
- 입력에 한글이 없을 때 (가정: 한국어 → 영어/일본어 방향만 번역)
- 글자 수가 200자를 넘을 때

### 5-3. 후보 탭 → 교체
입력 중이던 어절의 **글자 수만큼** `deleteBackward()` → 번역 `insertText()`. 탭하는 순간 한글 조합 상태를 먼저 확정·초기화해서 글자가 꼬이지 않게 합니다.

### 5-4. 한글 오토마타
- 상태: 초성 / 중성 / 종성 + 겹모음·겹받침 결합표
- 입력: 자모 1개 또는 삭제 → 출력: "확정된 글자" + "조합 중인 글자"
- 핵심 규칙: 종성 뒤에 모음이 오면 종성이 다음 글자의 초성으로 이동 (겹받침은 뒤쪽 자음만 이동: 닭+ㅣ → 달기)
- 삭제는 자모 단위로 한 단계씩 되돌림
- 테스트 30개 이상: 안녕하세요, 값이, 닭이, 읽어요, 왜, 괜찮아, 쌍자음, 연속 삭제, 조합 중 띄어쓰기 등

## 6. Phase별 산출물과 확인 방법

| Phase | 제가 만드는 것 | 리노님이 확인하는 것 |
|---|---|---|
| 0 | 이 문서 | 아래 질문에 답하고 승인 |
| 1 | `project.yml`, 타깃 3개, App Group, Shared 패키지, Mock 번역, 자동 빌드 설정 | Mac에서 명령 2줄 → Xcode에서 ▶ → 빈 화면 앱 실행 |
| 2 | `linotalk/server` 전체 + 테스트 + curl 예시 | (선택) 로컬 실행. API 키 발급은 이때 안내 |
| 3 | 영어 QWERTY + 후보 줄 + 탭 교체 (Mock) | 시뮬레이터 메모 앱에서 키보드 추가 후 타자 |
| 4 | 한글 오토마타 + 테스트 30개+ | 테스트 통과 화면, 한글 타자 |
